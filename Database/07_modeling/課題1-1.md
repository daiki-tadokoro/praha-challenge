## 課題1-1

サービスに新しく退会機能を加えることになりました。
とあるエンジニアは、登録しているユーザーが退会済みか否か判断できるよう以下のようなフラグを追加しました。

```sql
TABLE Student {
  id: varchar
  name: varchar
  taikaiFlag: boolean <- これを追加
}
```

この対応にはどのような問題点が潜んでいるでしょうか？

こちらは「とりあえず削除フラグ」という名前のついた有名なアンチパターンです。このフレーズで調べてみると良いかもしれません！

### とりあえず削除フラグの目的

ユーザには表示したくないが、データとしては消さずに残したい

### 問題点

#### 1. クエリの複雑化
常にWHERE文が必要になり、削除フラグだらけになり認識の語弊が生まれやすい。

```sql
-- 退会していないユーザーを取得
select *
from Student
where taikaiFlag = 0

-- 退会済みユーザーを取得
select *
from Student
where taikaiFlag = 1

-- 全ユーザーを取得（退会済み含む）
select *
from Student
```

#### 2. 開発者の負担増加
- 全てのクエリでWHERE句を忘れずに書く必要がある
- フラグの意味が曖昧になりやすい（0=有効、1=無効？それとも逆？）
- 新しい開発者が参加した際の学習コストが高い

#### 3. パフォーマンスの問題
- インデックスが効きにくい
- フラグの値が偏っている場合（例：退会済みが少ない）、統計情報が不正確になる

#### 4. データ整合性の問題
- フラグの更新忘れによる不整合
- 複数のテーブルでフラグ管理が必要になった場合の同期問題

#### 5. ビジネスロジックの複雑化
- 退会日時、退会理由などの追加情報が必要になった場合の対応が困難
