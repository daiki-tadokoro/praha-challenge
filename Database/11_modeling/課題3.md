## 外部キー制約と参照アクションに関するクイズ

### クイズ1: オンラインショッピングサイトの注文システム

あるオンラインショッピングサイトでは、以下のようなテーブル構造があります：
- `users` テーブル（ユーザー情報）
- `orders` テーブル（注文情報、`user_id`でusersテーブルを参照）
- `order_items` テーブル（注文商品詳細、`order_id`でordersテーブルを参照）

このシステムで、`orders`テーブルの`user_id`に`ON DELETE CASCADE`を設定した場合、どのような問題が発生する可能性があるでしょうか？また、より適切な参照アクションは何でしょうか？

### クイズ2: ブログシステムのコメント機能

ブログシステムで以下のテーブル構造を考えます：
- `posts` テーブル（ブログ記事）
- `comments` テーブル（コメント、`post_id`でpostsテーブルを参照）
- `users` テーブル（ユーザー情報）
- `comments` テーブルには`user_id`も含まれる（コメント投稿者）

このシステムで、`comments`テーブルの`post_id`に`ON DELETE SET NULL`を設定した場合、どのような問題が発生するでしょうか？また、この場合の最適な参照アクションは何でしょうか？

### クイズ3: 社内SNSの投稿システム

### クイズの回答例

#### クイズ1の回答例
**問題点**:
- ユーザー削除時に、そのユーザーの全ての注文履歴が消失する
- 売上データや分析データが失われる
- 返品・交換対応時に注文履歴が参照できない

**適切な参照アクション**:
- `ON DELETE RESTRICT`: 注文履歴があるユーザーは削除できないようにする
- または、ユーザーを論理削除（`deleted_at`フラグ）にして、物理削除は行わない

#### クイズ2の回答例
**問題点**:
- 記事削除時にコメントが宙に浮いた状態になる
- コメントの`post_id`がNULLになり、どの記事へのコメントか分からなくなる
- データベースの整合性が保たれない

**最適な参照アクション**:
- `ON DELETE CASCADE`: 記事削除時にコメントも削除する
- または、`ON DELETE RESTRICT`: コメントがある記事は削除できないようにする

#### クイズ3の回答例
**推奨設定**:
- `posts.author_id`: `ON DELETE RESTRICT` - 投稿がある従業員は削除できない
- `likes.user_id`: `ON DELETE CASCADE` - 従業員削除時にその人のいいねも削除
- `likes.post_id`: `ON DELETE CASCADE` - 投稿削除時にその投稿へのいいねも削除

**理由**:
- 投稿は社内の知識資産として残すべき
- いいねは個人的な反応なので、従業員削除時に削除して問題ない
- 投稿削除時は関連するいいねも削除するのが自然
