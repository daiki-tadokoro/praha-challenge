## 課題2-1

外部キー制約を作成する際には「ON DELETE CASCADE」など**参照アクション**を定義できます。MySQLで選択可能な参照アクションと、それぞれの参照アクションを選択すべきケースを挙げてください。

### 回答

MySQLで選択可能な参照アクションは以下の通りです：

#### 1. CASCADE
- **動作**: 親レコードが削除されると、関連する子レコードも自動的に削除される
- **選択すべきケース**: 
  - 親子関係が強い依存関係にある場合（例：ブログ記事とコメント）
  - 親が削除されたら子も意味をなさない場合
  - データの整合性を保つために子も削除する必要がある場合

#### 2. SET NULL
- **動作**: 親レコードが削除されると、子レコードの外部キーがNULLに設定される
- **選択すべきケース**:
  - 子レコードは残す必要があるが、親との関連を解除したい場合
  - オプショナルな関係の場合（例：ユーザーとプロフィール画像）
  - 履歴データを保持したい場合

#### 3. RESTRICT
- **動作**: 子レコードが存在する場合、親レコードの削除を拒否する
- **選択すべきケース**:
  - 重要な親子関係を保護したい場合
  - 誤削除を防ぎたい場合
  - 削除前に子レコードの処理を明示的に行いたい場合

#### 4. NO ACTION
- **動作**: RESTRICTと同様に、子レコードが存在する場合に親レコードの削除を拒否する
- **選択すべきケース**:
  - 標準的な参照整合性を保ちたい場合
  - 削除の制約を設けたい場合

#### 5. SET DEFAULT
- **動作**: 親レコードが削除されると、子レコードの外部キーがデフォルト値に設定される
- **選択すべきケース**:
  - デフォルトの親レコードが存在する場合
  - 特定のデフォルト値に戻したい場合

## 課題2-2

いくつかユースケースを考えながら、適切な参照アクションを選択してみましょう

従業員管理サービスを例に考えてみます。
従業員（Employeeテーブルがあるとします）は必ず部署（Departmentテーブルがあるとします）に所属していなければいけないとします。
Employeeテーブルには`department_id`カラムが含まれていて、`ON DELETE CASCADE`が設定されています。このケースにはどのような問題が潜んでいるでしょうか？

### 回答

このケースには以下のような深刻な問題が潜んでいます：

#### 1. **データの意図しない削除**
- 部署を削除すると、その部署に所属する全ての従業員も自動的に削除されてしまう
- 部署の統廃合や再編成時に、従業員データが失われる可能性がある
- 人事異動の前に部署を削除してしまうと、従業員情報が消失する

#### 2. **ビジネスロジックとの不整合**
- 「従業員は必ず部署に所属していなければいけない」という要件と矛盾
- 部署削除時に従業員の再配置を検討する必要があるが、CASCADEでは検討の余地がない

#### 3. **履歴データの消失**
- 過去の部署所属履歴が失われる
- 給与計算や人事評価の履歴が不正確になる可能性

#### 4. **適切な代替案**
このケースでは以下の参照アクションが適切です：

- **RESTRICT**: 部署に従業員が所属している限り、部署の削除を拒否する
- **SET NULL + 制約**: 部署削除時に従業員の部署IDをNULLに設定し、別途制約でNULLを許可しない

#### 5. **推奨される解決策**
```sql
-- 部署削除前に従業員の再配置を強制
ALTER TABLE Employee 
ADD CONSTRAINT fk_employee_department 
FOREIGN KEY (department_id) 
REFERENCES Department(id) 
ON DELETE RESTRICT;
```

## 課題2-3

プロジェクトマネジメントツールを例に考えてみます。
このサービスでは案件（Issueテーブルがあるとします）には必ず担当者（Assigneeテーブルがあるとします）が任命されなければならず、担当者が任命されていないIssueが存在することはサービスの性質上、一切許容されません。
Issueテーブルには`assignee_id`カラムが含まれていて、`on delete set null`が設定されていました。
このケースにはどのような問題が潜んでいるでしょうか？

### 回答

このケースには以下のような深刻な問題が潜んでいます：

#### 1. **ビジネスルールの違反**
- 「案件には必ず担当者が任命されなければいけない」という要件と完全に矛盾
- `SET NULL`により、担当者が削除されると案件の`assignee_id`がNULLになり、要件違反の状態になる

#### 2. **データ整合性の破綻**
- 担当者なしの案件が発生し、システムの動作に支障をきたす可能性
- 案件の進捗管理や責任の所在が不明確になる

#### 3. **ユーザー体験の悪化**
- 担当者が削除された案件が宙に浮いた状態になり、ユーザーが混乱する
- 案件の再割り当てが自動的に行われない

#### 4. **適切な代替案**
このケースでは以下の参照アクションが適切です：

- **RESTRICT**: 担当者が案件を抱えている限り、担当者の削除を拒否する
- **CASCADE**: 担当者削除時に案件も削除する（案件が担当者に強く依存している場合）

#### 5. **推奨される解決策**
```sql
-- 担当者削除前に案件の再割り当てを強制
ALTER TABLE Issue 
ADD CONSTRAINT fk_issue_assignee 
FOREIGN KEY (assignee_id) 
REFERENCES Assignee(id) 
ON DELETE RESTRICT;
```

または、担当者削除時の処理をアプリケーションレベルで制御：

```sql
-- 担当者削除時にデフォルト担当者に再割り当て
UPDATE Issue 
SET assignee_id = (SELECT id FROM Assignee WHERE is_default = true LIMIT 1)
WHERE assignee_id = [削除される担当者ID];
```

## 課題2-4

PrismaやTypeORMなど任意のORMを2つ選んで、参照アクションにどのようなデフォルト値を設定しているか調べて、その値が選択されている理由を考えてみてください。

MySQLとPostgreSQLでは`restrict`と`no action`の扱いに少し違いがあります。それはどのような違いでしょうか？

### 回答

#### Prismaのデフォルト設定

**デフォルト値**: `onDelete: ReferentialAction.Restrict`

**選択理由**:
- **安全性重視**: 意図しないデータ削除を防ぐ
- **明示的な制御**: 削除処理をアプリケーションレベルで制御できる
- **データ保護**: 重要なデータの誤削除を防ぐ
- **開発者の意識向上**: 削除の影響を意識して設計することを促す

#### TypeORMのデフォルト設定

**デフォルト値**: `onDelete: "NO ACTION"`

**選択理由**:
- **標準準拠**: SQL標準に準拠した動作
- **データベース依存**: 各データベースのデフォルト動作に従う
- **柔軟性**: 開発者が明示的に設定することを前提
- **互換性**: 異なるデータベース間での互換性を保つ

#### 両ORMの共通点
- どちらも**安全側**のデフォルトを選択
- 開発者が意図的に参照アクションを設定することを促す
- データの整合性保護を重視

#### MySQLとPostgreSQLの`RESTRICT`と`NO ACTION`の違い

**MySQL**:
- `RESTRICT`: 即座にチェック（IMMEDIATE）
- `NO ACTION`: 遅延チェック（DEFERRED）をサポート
- 実用上はほぼ同じ動作

**PostgreSQL**:
- `RESTRICT`: 即座にチェック（IMMEDIATE）
- `NO ACTION`: 遅延チェック（DEFERRED）をサポート
- トランザクション内での動作が異なる

**主な違い**:
1. **チェックタイミング**:
   - `RESTRICT`: 各ステートメント実行時に即座にチェック
   - `NO ACTION`: トランザクション終了時にチェック（DEFERREDの場合）

2. **トランザクション内での動作**:
   ```sql
   -- PostgreSQLでの例
   BEGIN;
   DELETE FROM parent WHERE id = 1;  -- NO ACTIONの場合、ここではエラーにならない
   UPDATE child SET parent_id = 2 WHERE parent_id = 1;  -- 関連を変更
   COMMIT;  -- ここでNO ACTIONのチェックが実行される
   ```

3. **実用上の推奨**:
   - ほとんどの場合、`RESTRICT`を使用
   - 複雑なトランザクション処理が必要な場合のみ`NO ACTION`を検討
