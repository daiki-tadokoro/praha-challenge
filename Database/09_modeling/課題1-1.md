## 課題1-1

MySQLやPostgreSQLには「Check」「Enum」「Domain」「Trigger」など、システムの仕様をデータベースに強制するために様々な機能が用意されています。

以下のケースを読みながら、どのような状況で上記機能を使うべきか、どのような状況で使うべきではないか、考えてみてください！

本サービスには「User」というテーブルが用意されていると仮定します


### 「mailAddress」カラムには、特定のドメインを持ったメールアドレスしか登録できない（a@example.com, b@example.comなど）。

**Checkを使うべきでしょうか？**

**回答: Checkは使うべきではない**

**理由:**

#### 1. **ビジネスルールの変更可能性**
- 許可するドメインリストは頻繁に変更される可能性がある
- 新しいドメインの追加や削除が発生する
- Check制約の変更にはALTER TABLEが必要で、運用負荷が高い

#### 2. **複雑なバリデーションロジック**
- メールアドレスの形式チェック（@の存在、ドメイン形式など）
- ドメインの有効性確認
- 複数のドメインに対する柔軟な制御


**Check制約を使うべき場合:**

####  **単純で安定した制約**
```sql
-- 年齢制限の例
CREATE TABLE User (
    id INT PRIMARY KEY,
    name VARCHAR(255),
    age INT CHECK (age >= 0 AND age <= 150)
);
```

### ユーザーが退会した時、当該ユーザーのレコードを「User」テーブルから削除し、同じ情報を「WithdrawnUser」テーブルに挿入しなければいけない。

**Triggerを使うべきでしょうか？**

**回答: Triggerは使うべきではない**

**理由:**

#### 1. **デバッグの困難さ**
- Triggerは「見えない」処理のため、問題発生時の原因特定が困難
- ログが残りにくく、トラブルシューティングが複雑

#### 2. **テストの複雑さ**
- Triggerの動作をテストするには、実際のデータベース操作が必要
- 単体テストが困難で、統合テストに依存

#### 3. **パフォーマンスの問題**
- 毎回のDELETE操作でTriggerが実行され、パフォーマンスに影響
- 大量データ処理時の性能劣化

#### 4. **ビジネスロジックの分散**
- データベースとアプリケーションの両方にビジネスロジックが分散
- 保守性の低下

#### 5. **トランザクション管理の複雑さ**
- Trigger内でのエラーハンドリングが複雑
- ロールバック時の動作が予測が難しい


### 「gender」カラムには「male」「female」「no response」いずれかの値しか入れてはいけない。

**Enumを使うべきでしょうか？**

**回答: Enumを使うべき**

**理由:**

#### 1. **データ整合性の保証**
- データベースレベルで制約が強制される
- アプリケーション側のバグによる不正値の挿入を防げる

#### 2. **パフォーマンスの向上**
- 文字列比較より数値比較の方が高速
- インデックス効率が良い

#### 3. **ストレージ効率**
- 文字列より数値の方がストレージ容量が小さい
- 例：'male'（4バイト）→ 1（1バイト）

#### 4. **明確な制約定義**
- スキーマを見るだけで制約が明確
- ドキュメント化が不要

#### 5. **変更の困難さ**
- 一度定義すると変更が困難なため、安易な変更を防げる
- ビジネスルールの安定性を保証


### 「postCode」カラムには特定形式の文字列しか入れてはいけない。

**Domainを使うべきでしょうか？**

### Domainとは？

#### 定義
**Domain**とは、PostgreSQLで提供される機能で、既存のデータ型に制約やデフォルト値を追加して、新しいカスタムデータ型を作成する機能です。

#### 特徴
- **再利用可能**: 一度定義すると複数のテーブルで使用可能
- **制約付き**: CHECK制約やNOT NULL制約を組み込み可能
- **デフォルト値**: デフォルト値を設定可能
- **型安全性**: データ型の安全性を保証

#### 基本的な構文
```sql
CREATE DOMAIN domain_name AS data_type
    [DEFAULT default_value]
    [CONSTRAINT constraint_name CHECK (condition)];
```

**回答: ケースによる（PostgreSQLの場合）**

**理由:**

#### PostgreSQLの場合（Domain使用推奨）
```sql
-- Domain定義
CREATE DOMAIN post_code AS VARCHAR(10)
    CONSTRAINT valid_post_code 
    CHECK (VALUE ~ '^[0-9]{3}-[0-9]{4}$');

-- テーブル定義
CREATE TABLE User (
    id INT PRIMARY KEY,
    name VARCHAR(255),
    post_code post_code
);
```

**Domainを使うべき理由:**
1. 複数のテーブルで同じ郵便番号制約を使用できる
2. 郵便番号の形式が統一される
3. 制約の変更が一箇所で済む
4. スキーマを見るだけで制約が明確

#### MySQLの場合（CHECK制約使用）
```sql
CREATE TABLE User (
    id INT PRIMARY KEY,
    name VARCHAR(255),
    post_code VARCHAR(10) CHECK (post_code REGEXP '^[0-9]{3}-[0-9]{4}$')
);
```

**CHECK制約を使う理由:**
1. MySQLではDomain機能がない
2. 単一テーブルでの制約なら十分
3. 多くのデータベースでサポート

#### アプリケーション側制御の場合
```sql
CREATE TABLE User (
    id INT PRIMARY KEY,
    name VARCHAR(255),
    post_code VARCHAR(10)
);
```

**アプリケーション側制御を使う理由:**
1. 国際化対応が必要
2. 郵便番号形式の変更が頻繁
3. ユーザーフレンドリーなエラー表示
4. 単体テストが簡単


### アプリケーション側とデータベース側の制約の使い分け

#### データベース側で制約を課すべき場合:

1. **データの整合性が重要な場合**
   - 金融取引データ
   - 在庫管理システム
   - 会計システム

2. **複数のアプリケーションからアクセスする場合**
   - マイクロサービスアーキテクチャ
   - レガシーシステムとの共存
   - 他社システムとの連携

3. **パフォーマンスが重要な場合**
   - 大量データの一括処理
   - トランザクション処理
   - インデックス最適化

4. **制約が安定していて変更の少ない場合**
   - 郵便番号の形式（123-4567）
   - 電話番号の形式（090-1234-5678）
   - 年齢制限（0-110歳）
   - 価格制限（0以上）

#### アプリケーション側で制約を課すべき場合:

1. **ユーザー体験を重視する場合**
   - リアルタイムバリデーション
   - カスタマイズ可能な入力形式
   - 多言語対応のエラーメッセージ

2. **ビジネスロジックが複雑な場合**
   - 条件分岐の多い検証
   - 外部APIとの連携
   - 動的なルール変更

3. **開発・保守性を重視する場合**
   - 単体テストの容易さ
   - 頻繁な仕様変更
   - デプロイの柔軟性

4. **制約が頻繁に変更される場合**
   - 許可するメールドメインの変更
   - パスワードポリシーの変更
   - 国別の住所形式対応

#### ベストプラクティス:
- 重要なデータ整合性はDB側で
- UI/UX関連の制約はアプリケーション側で
- 両方を組み合わせた多層防御の採用もあり

- **安定した制約はDB側、変更される可能性がある制約はアプリケーション側**
