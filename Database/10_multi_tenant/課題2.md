# マルチテナントアーキテクチャのパターンとPostgreSQL RLS実装

## 課題2-1: マルチテナントアーキテクチャのパターン

### 1. テナント毎にデータベースを分割する（Database per Tenant）

#### アーキテクチャ概要
```
Tenant A → Database A
Tenant B → Database B
Tenant C → Database C
```

#### メリット
- **完全なデータ分離**: 物理的にデータが分離されるため、データ漏洩のリスクが極めて低い
- **スキーマの柔軟性**: 各テナントで異なるスキーマ設計が可能
- **パフォーマンス**: テナント間の競合がなく、クエリパフォーマンスが高い
- **バックアップ・復旧**: テナント単位でのバックアップ・復旧が容易
- **スケーラビリティ**: テナントごとに異なるリソース割り当てが可能
- **カスタマイズ性**: テナント固有の機能やデータ構造を実装可能

#### デメリット
- **運用コスト**: データベース数がテナント数に比例して増加
- **リソース消費**: 各データベースがメモリ・CPU・ディスクを消費
- **管理の複雑性**: 多数のデータベースの管理・監視が困難
- **開発コスト**: スキーマ変更時の全データベースへの適用が必要

#### 実装例
```sql
-- テナントA用データベース
CREATE DATABASE tenant_a_db;
USE tenant_a_db;

CREATE TABLE employees (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    department VARCHAR(100),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- テナントB用データベース
CREATE DATABASE tenant_b_db;
USE tenant_b_db;

CREATE TABLE employees (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    position VARCHAR(100), -- 異なるカラム
    hire_date DATE,        -- 異なるカラム
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 2. すべてのテナントで同じスキーマを使う（Shared Schema）

#### アーキテクチャ概要
```
Database
└── employees (tenant_id で分離)
    ├── tenant_id = 'A' のレコード
    ├── tenant_id = 'B' のレコード
    └── tenant_id = 'C' のレコード
```

#### メリット
- **コスト効率**: 最も低コストで実装・運用可能
- **管理の簡素化**: 単一スキーマの管理で済む
- **開発効率**: スキーマ変更が1箇所で済む
- **リソース効率**: 最小限のリソースで多数のテナントを管理
- **スケーラビリティ**: テナント数の増加に柔軟に対応
- **統一性**: 全テナントで一貫したデータ構造

#### デメリット
- **データ分離の複雑性**: アプリケーションレベルでの分離が必要
- **セキュリティリスク**: 実装ミスによるデータ漏洩のリスク
- **パフォーマンス**: テナントIDでのフィルタリングが必要
- **カスタマイズ性**: テナント固有の要件に対応しにくい
- **監査の複雑性**: テナント間の操作を区別する必要

#### 実装例
```sql
-- 共有スキーマ
CREATE TABLE employees (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    tenant_id VARCHAR(50) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- インデックス
CREATE INDEX idx_employees_tenant_id ON employees(tenant_id);

-- サンプルデータ
INSERT INTO employees (name, email, tenant_id) VALUES
    ('user1', 'tanaka@company-a.com', 'tenant_a'),
    ('user2', 'sato@company-a.com', 'tenant_a'),
    ('user3', 'yamada@company-b.com', 'tenant_b'),
    ('user4', 'suzuki@company-b.com', 'tenant_b');
```

## 課題2-2: PostgreSQL RLS（Row-Level Security）の実装

### RLSとは

PostgreSQLのRow-Level Security（RLS）は、行レベルでのセキュリティを提供する機能です。テーブルにポリシーを設定することで、特定の条件を満たす行のみにアクセスを制限できます。

ref: https://zenn.dev/taxin/articles/postgresql-row-level-security-policy

### RLSの基本概念

1. **ポリシー**: 行へのアクセス条件を定義
2. **セッション変数**: 現在のユーザーやテナント情報を格納
3. **USING句**: SELECT、DELETE、UPDATE時の条件
4. **WITH CHECK句**: INSERT、UPDATE時の条件

### マルチテナント環境でのRLS実装

#### 1. 基本的なテーブル設計

```sql
-- テナントテーブル
CREATE TABLE tenants (
    id VARCHAR(50) PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    status VARCHAR(20) DEFAULT 'active',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 従業員テーブル（マルチテナント対応）
CREATE TABLE employees (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    department VARCHAR(100),
    tenant_id VARCHAR(50) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    
    -- 外部キー制約
    FOREIGN KEY (tenant_id) REFERENCES tenants(id),
    
    -- ユニーク制約（テナント内でメールアドレスは一意）
    UNIQUE (email, tenant_id)
);

-- インデックス
CREATE INDEX idx_employees_tenant_id ON employees(tenant_id);
CREATE INDEX idx_employees_email ON employees(email);
```

#### 2. RLSの有効化

```sql
-- RLSを有効化
ALTER TABLE employees ENABLE ROW LEVEL SECURITY;

-- デフォルトポリシー（何もアクセスできない）
CREATE POLICY default_deny ON employees
    FOR ALL
    USING (false);
```

#### 3. セッション変数管理

```sql
-- セッション変数を設定する関数
CREATE OR REPLACE FUNCTION set_tenant_id(tenant_id VARCHAR(50))
RETURNS VOID AS $$
BEGIN
    -- セッション変数にテナントIDを設定
    PERFORM set_config('app.current_tenant_id', tenant_id, false);
    
    -- ログ出力（デバッグ用）
    RAISE NOTICE 'Tenant ID set to: %', tenant_id;
END;
$$ LANGUAGE plpgsql;

-- 現在のテナントIDを取得する関数
CREATE OR REPLACE FUNCTION get_current_tenant_id()
RETURNS VARCHAR(50) AS $$
BEGIN
    RETURN current_setting('app.current_tenant_id', true);
END;
$$ LANGUAGE plpgsql;
```

#### 4. RLSポリシーの作成

```sql
-- SELECTポリシー（読み取り）
CREATE POLICY tenant_isolation_select ON employees
    FOR SELECT
    USING (tenant_id = get_current_tenant_id());

-- INSERTポリシー（挿入）
CREATE POLICY tenant_isolation_insert ON employees
    FOR INSERT
    WITH CHECK (tenant_id = get_current_tenant_id());

-- UPDATEポリシー（更新）
CREATE POLICY tenant_isolation_update ON employees
    FOR UPDATE
    USING (tenant_id = get_current_tenant_id())
    WITH CHECK (tenant_id = get_current_tenant_id());

-- DELETEポリシー（削除）
CREATE POLICY tenant_isolation_delete ON employees
    FOR DELETE
    USING (tenant_id = get_current_tenant_id());
```

#### 5. 監査機能の追加

```sql
-- 監査ログテーブル
CREATE TABLE audit_logs (
    id SERIAL PRIMARY KEY,
    table_name VARCHAR(50) NOT NULL,
    operation VARCHAR(10) NOT NULL, -- INSERT, UPDATE, DELETE, SELECT
    tenant_id VARCHAR(50),
    user_id VARCHAR(50),
    old_data JSONB,
    new_data JSONB,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 監査トリガー関数
CREATE OR REPLACE FUNCTION audit_trigger_function()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO audit_logs (table_name, operation, tenant_id, new_data)
        VALUES (TG_TABLE_NAME, TG_OP, NEW.tenant_id, to_jsonb(NEW));
        RETURN NEW;
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO audit_logs (table_name, operation, tenant_id, old_data, new_data)
        VALUES (TG_TABLE_NAME, TG_OP, NEW.tenant_id, to_jsonb(OLD), to_jsonb(NEW));
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO audit_logs (table_name, operation, tenant_id, old_data)
        VALUES (TG_TABLE_NAME, TG_OP, OLD.tenant_id, to_jsonb(OLD));
        RETURN OLD;
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

-- 監査トリガーの作成
CREATE TRIGGER employees_audit_trigger
    AFTER INSERT OR UPDATE OR DELETE ON employees
    FOR EACH ROW EXECUTE FUNCTION audit_trigger_function();
```

#### 6. アプリケーション連携（Go実装例）

```go
package main

import (
    "context"
    "database/sql"
    "fmt"
    _ "github.com/lib/pq"
)

type TenantRepository struct {
    db *sql.DB
}

func NewTenantRepository(db *sql.DB) *TenantRepository {
    return &TenantRepository{db: db}
}

// セッションにテナントIDを設定
func (r *TenantRepository) SetTenantID(ctx context.Context, tenantID string) error {
    query := `SELECT set_tenant_id($1)`
    _, err := r.db.ExecContext(ctx, query, tenantID)
    if err != nil {
        return fmt.Errorf("failed to set tenant ID: %w", err)
    }
    return nil
}

// テナント内の全従業員を取得（RLSにより自動的にフィルタリング）
func (r *TenantRepository) GetAllEmployees(ctx context.Context) ([]*Employee, error) {
    // セッションにテナントIDを設定
    tenant, err := GetTenantFromContext(ctx)
    if err != nil {
        return nil, fmt.Errorf("tenant context required: %w", err)
    }
    
    if err := r.SetTenantID(ctx, tenant.ID); err != nil {
        return nil, err
    }
    
    // RLSにより自動的にテナントIDでフィルタリングされる
    query := `SELECT id, name, email, department, tenant_id, created_at, updated_at FROM employees`
    rows, err := r.db.QueryContext(ctx, query)
    if err != nil {
        return nil, fmt.Errorf("failed to query employees: %w", err)
    }
    defer rows.Close()
    
    var employees []*Employee
    for rows.Next() {
        emp := &Employee{}
        if err := rows.Scan(&emp.ID, &emp.Name, &emp.Email, &emp.Department, &emp.TenantID, &emp.CreatedAt, &emp.UpdatedAt); err != nil {
            return nil, fmt.Errorf("failed to scan employee: %w", err)
        }
        employees = append(employees, emp)
    }
    
    return employees, nil
}

// 新しい従業員を作成（RLSにより自動的にテナントIDが設定される）
func (r *TenantRepository) CreateEmployee(ctx context.Context, name, email, department string) (*Employee, error) {
    tenant, err := GetTenantFromContext(ctx)
    if err != nil {
        return nil, fmt.Errorf("tenant context required: %w", err)
    }
    
    if err := r.SetTenantID(ctx, tenant.ID); err != nil {
        return nil, err
    }
    
    // RLSにより自動的にテナントIDが検証される
    query := `INSERT INTO employees (name, email, department, tenant_id) VALUES ($1, $2, $3, $4) RETURNING id, name, email, department, tenant_id, created_at, updated_at`
    emp := &Employee{}
    err = r.db.QueryRowContext(ctx, query, name, email, department, tenant.ID).Scan(
        &emp.ID, &emp.Name, &emp.Email, &emp.Department, &emp.TenantID, &emp.CreatedAt, &emp.UpdatedAt)
    if err != nil {
        return nil, fmt.Errorf("failed to create employee: %w", err)
    }
    
    return emp, nil
}
```

### RLSの高度な機能

#### 1. 条件付きポリシー

```sql
-- アクティブなテナントのみアクセス可能
CREATE POLICY active_tenant_only ON employees
    FOR ALL
    USING (
        tenant_id = get_current_tenant_id() 
        AND EXISTS (
            SELECT 1 FROM tenants 
            WHERE id = get_current_tenant_id() 
            AND status = 'active'
        )
    );
```

#### 2. 時間ベースのポリシー

```sql
-- 営業時間内のみアクセス可能
CREATE POLICY business_hours_only ON employees
    FOR SELECT
    USING (
        tenant_id = get_current_tenant_id()
        AND EXTRACT(HOUR FROM CURRENT_TIME) BETWEEN 9 AND 18
    );
```

#### 3. ロールベースのポリシー

```sql
-- 管理者のみ削除可能
CREATE POLICY admin_delete_only ON employees
    FOR DELETE
    USING (
        tenant_id = get_current_tenant_id()
        AND current_setting('app.user_role', true) = 'admin'
    );
```

    AND created_at > CURRENT_DATE - INTERVAL '7 days'

## まとめ（この辺はAIがまとめてくれました）

### アーキテクチャパターンの選択指針

1. **Database per Tenant**: 最高レベルのセキュリティが必要で、コストを気にしない場合
2. **Shared Schema + RLS**: コスト効率を重視し、PostgreSQLを使用できる場合（推奨）
3. **Schema per Tenant**: テナントごとに根本的に異なるスキーマ構造が必要な場合のみ

### PostgreSQL RLSの利点

- **強力なセキュリティ**: DBレベルでの強制力
- **パフォーマンス**: 効率的なフィルタリング
- **開発効率**: アプリケーションコードが簡潔
- **監査機能**: 詳細なアクセスログ
- **柔軟性**: 複雑な条件も設定可能

### 実装のベストプラクティス

1. **段階的な導入**: まずは基本的なRLSから始める
2. **十分なテスト**: テナント分離の動作を徹底的にテスト
3. **監視の実装**: アクセスログとアラートを設定
4. **ドキュメント化**: ポリシーと運用方法を文書化
5. **定期的な見直し**: セキュリティ要件の変化に対応
